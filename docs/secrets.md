# 沙箱密钥

沙箱里跑的是不可信代码。密钥一旦进入容器，Agent 就能读走。本文只记录问题和做法，暂不实现。

## 1. 现状

敏感信息没有单独的资源，和普通配置走同一条路。

- 模板的环境变量、创建沙箱时追加的环境变量，原样交给 Sealos Launchpad，成为容器环境变量。
- 模板的配置文件挂载（configMap）把全文写进容器里的文件。

容器里的进程可以执行 `env`，也可以用 `read` / `exec` 读文件。沙箱默认可访问公网，读到的值可以被发给任意地址。提示词注入、恶意依赖、交互式命令都能触发这件事。

把值放进 Kubernetes Secret 再挂成环境变量或文件，结果相同：挂进容器之后，不可信代码仍然读得到。

## 2. 定义

这个场景叫 **不可信执行环境中的密钥注入（secret injection into an untrusted runtime）**。

要分开两件事：

- **密钥落盘 / 进入运行时（materialization）**：明文出现在环境变量、文件、进程参数或接口响应里。
- **密钥外带（secret exfiltration）**：运行时代码把读到的明文发到外部。

Agent 沙箱的目标是 **密钥不进入工作负载（secrets stay outside the workload）**。运行时代码需要访问 GitHub、npm 或模型 API 时，由控制面做 **凭证代理（credential brokering）**：在沙箱外面代表它完成认证。

配置里只保存 **密钥引用（secret reference）**，不保存明文。引用在受信任的一侧解析。

## 3. 业界怎么解决的

Agent 沙箱的标准做法是 **出网代理注入（egress secret injection）**，E2B Secrets 是这个模型。

1. 密钥存在控制面，接口只写不回读，库内加密。
2. 绑定写明：哪台沙箱、哪些域名、补哪个 HTTP 头。一个域名只绑一个密钥。
3. 沙箱访问这些域名时不携带密钥。流量离开沙箱后，出口网关按 TLS 域名匹配绑定，再补上 header 并转发。
4. 网关故障时拒绝出网，不退回沙箱直连。日志只记沙箱、域名和密钥名，不记值。
5. 只向信任的域名注入。对方若把请求头回显进响应，沙箱仍能看到这一次的值。

Git、curl、npm 都是普通的 HTTPS，网关不按客户端区分。域名列表是放行范围。GitHub、npm 这类常用目的地用预设填好域名和 header 格式。

1Password 的 `op run` 解决的是另一件事：仓库和 CI 配置里放 `op://保险库/条目/字段` 这种引用，运行前由本机 `op` 换成明文，再注入子进程的环境变量。明文仍然进入该进程。服务账号令牌若放进沙箱，沙箱就能读取该令牌获准的全部密钥。它适合可信的 CI，不适合不可信沙箱。

SSH 代理是更近的一类：私钥留在代理里，工作负载只拿到签名结果。数据库、SSH 等不能靠 HTTP header 注入的协议，用短时、收窄权限的凭证，并接受明文会短暂出现在进程中。

## 4. 本项目可以怎么解决

方向如下。

环境变量和配置文件只放非机密配置。密钥单独建资源：只写不回读，加密存储，按模板或沙箱绑定域名和 header。创建沙箱时不把密钥写入 Launchpad 的 `env` 或 configMap。管理密钥只允许登录会话，不允许沙箱内的 API Key。

集群内单独部署出口网关。沙箱的 HTTPS 先到网关，网关按来源 Pod 注入 header。控制台为 GitHub、npm 等提供预设。沙箱 Pod 不挂载 ServiceAccount，避免它从 Kubernetes API 读到 Secret。

非 HTTPS 协议不走这套注入。必须由沙箱直连时，再发放短时凭证。
